# M2 — ativação local controlada da coleta

O serviço de leitura agora aceita `WR3D_MONITORING_CONFIG_PATH` para iniciar sondas locais de host, HTTP e Docker opt-in junto do snapshot/SSE. Sem essa variável, continua inerte: não cadastra inventário nem faz coleta. A configuração deve ficar fora do repositório, conter somente alvos expressamente autorizados e não incluir credenciais. Arquivos `*.monitoring.local.json` também estão ignorados pelo Git.

O JSON local tem `schemaVersion: "1.0"`, `projects` (identidade, nome e caminho absoluto), `inventory` conforme `contracts/schemas/resource.v1.schema.json`, `probes`, `intervalMs` e `timeoutMs`. O [exemplo versionado](../../../service/examples/monitoring.example.json) contém somente um projeto ilustrativo e uma sonda de memória do host; copie e adapte para um arquivo local antes de executar. Cada sonda deve apontar para um recurso do inventário com o mesmo tipo. São aceitos `{ "kind": "host", "resourceId": "..." }`, `{ "kind": "api", "resourceId": "...", "url": "http://127.0.0.1:.../health" }` e `{ "kind": "docker", "resourceId": "...", "containerName": "api-lab", "proxyUrl": "http://127.0.0.1:PORTA/v1/snapshot" }`. A sonda Docker exige recurso `kind: "docker"` e token de pelo menos 32 bytes em `WR3D_DOCKER_PROXY_TOKEN` no ambiente do serviço; o token não entra no JSON. Não há URL padrão. O serviço rejeita tipos adicionais, recursos sem correspondência, nomes de projeto acima do contrato, projetos duplicados e caminhos que colidem. Ao iniciar com configuração, o inventário persistido é substituído pelo conjunto completo informado; projetos já cadastrados devem manter os caminhos existentes. Cadastro de projetos e substituição do inventário ocorrem em uma transação: uma configuração incompatível não deixa projetos, salas ou avisos parciais. O `CollectorRunner` faz a primeira leitura após iniciar e agenda as próximas sem depender de sessões ou do Player.

Para rodar com uma configuração local aprovada, iniciar a partir de `service` com Node 24 e definir `WR3D_DATABASE_PATH` (SQLite fora do Git), `WR3D_SERVICE_PORT`, `WR3D_SERVICE_TOKEN` (valor aleatório com pelo menos 32 bytes) e `WR3D_MONITORING_CONFIG_PATH`; então executar `node src/http/main.ts`. O Player recebe a URL de loopback e o mesmo token por `WR3D_SERVICE_URL`/`WR3D_SERVICE_TOKEN`. O serviço recusa configuração inválida antes de abrir a porta. Em falha de sonda, registra cobertura perdida; não inventa incidente nem mantém saúde atual.

Esta ligação não inicia o proxy Docker nem comprova isolamento de identidade; apenas permite sua coleta periódica quando o proxy separado já está autorizado e ativo. A sonda SQL ainda requer papel, alvo, consulta aprovada e credencial local; o proxy Docker ainda requer identidade de execução isolada antes de coleta contínua. A autorização anterior para a API de produção cobriu três GET pontuais; não autoriza configurar coleta recorrente. Esses recursos ficam `not_run` até receberem escopo e permissões específicos.

## Validação desta fatia

Em 06/11/2026, Node 24.15.0: `npm run typecheck` e 48/48 testes do serviço passaram. Cinco testes novos cobriram: API sintética em loopback ligada a incidente, recuperação e snapshot autenticado sem sessões, com impacto apenas em dois projetos vinculados; rejeição de sonda Docker não autorizada e nome acima do contrato antes de cadastrar projetos; recusa de caminho novo em projeto existente; reversão atômica de projeto, sala e avisos quando a troca de ambiente de recurso é rejeitada; e processo standalone que coletou memória real do host local e a publicou como cobertura atual com saúde `sem_dados`, sem inferir saúde da máquina. Não houve consulta a serviço externo nesses testes.
