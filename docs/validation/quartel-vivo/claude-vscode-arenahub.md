# #49 — Claude Code no VS Code local, ArenaHub

Data: 10/11/2026. Estado: **fonte real parcial confirmada no serviço**, sem prova no Player. O PI indicou `D:\Desenvolvimento\Projetos\arenahub` como novo alvo local no Claude Code do VS Code, após o ensaio sem sinal do Codex no VS Code. Esta prova de um projeto não satisfaz a meta de dois projetos no Player.

## Escopo e ambiente

- Projeto autorizado: `arenahub`, branch `main`, HEAD inicial `80dcad98797ffa75b6eff3385e6f594e67e24e01`. A alteração não rastreada `.impeccable/config.local.json` já existia antes do ensaio. Uma modificação em `apps/admin-web/app/actions/membership.test.ts` foi observada depois; não foi feita nem alterada por esta integração.
- Extensão VS Code `anthropic.claude-code` `2.1.322`; binário empacotado `claude.exe` confirma `2.1.322 (Claude Code)`, SHA-256 `345996B4BDBAE21D817F750FAE2F34CBF8D81224A5444C78136091D121BEB298`. Dois processos locais desse binário estavam em execução durante o diagnóstico.
- A [documentação de configurações do Claude Code](https://code.claude.com/docs/en/settings) inclui a extensão VS Code nas superfícies locais que leem `.claude/settings.local.json`. O arquivo compartilhado `.claude/settings.json` preexistente tinha um hook `SessionStart` e não foi alterado.
- O PI autorizou hooks reversíveis somente neste projeto e confirmou chats novos na extensão, com execução local no workspace `D:\Desenvolvimento\Projetos\arenahub`. Não foram solicitados nem lidos prompts ou transcrições.

## Ensaio e privacidade

O arquivo local preexistente `.claude/settings.local.json` foi copiado antes da alteração, com SHA-256 `2775CB1496D074C037F5572DBF4C90291602C7A621927AEE2933C20017A0FAD2`. A primeira definição acrescentou nove hooks operacionais e tinha SHA-256 `8C24D7918753E1B5A0A3248AA5D18AF68A2DA94D0985029A8FF12D29460A883F`. O capturador aceitava apenas `SessionStart` de `startup` e sessões matriculadas depois dele; descartava prompt, transcrição, comando, argumentos, resposta de ferramenta e credenciais antes de qualquer gravação.

Após o primeiro chat sem spool, a segunda definição acrescentou um diagnóstico de `SessionStart` e `UserPromptSubmit` que gravaria somente o nome do evento e o horário, sem ler o `stdin`. Ela tinha SHA-256 `4973BDBB981C5B7CA5C8AE06ACAABF198BB7FB474BAFBFFD9B02AA12AD2A522E`. O PI concluiu outro chat novo local no mesmo workspace. Nem o spool sanitizado nem o marcador mínimo foram criados. Os comandos funcionaram quando chamados diretamente pelo PowerShell/`cmd.exe`, mas isso **não validava o shell de hooks do Claude**.

Ao verificar a configuração após o reinício do VS Code, foi identificado um erro no comando instalado: caminhos Windows com barras invertidas sem aspas. A execução sintética pelo Git Bash retornou `127` porque as barras foram consumidas e o executável não foi encontrado. O mesmo diagnóstico e a captura, com caminhos `/c/...`, saíram com `0` e gravaram seus arquivos sintéticos separados, depois removidos. Assim, os dois chats anteriores **não são evidência de falha da extensão**; a própria configuração do ensaio estava incorreta.

A configuração temporária corrigida continha `SessionStart` e `UserPromptSubmit`, cada um com capturador e marcador mínimo, e tinha SHA-256 `F53E145977FD219153859D986FB445A428A0133060CD8416FD8DB7AE6AF0A781`. Após o PI recarregar o VS Code e iniciar um chat novo, o diagnóstico registrou dois `SessionStart` e dois `UserPromptSubmit`; o spool sanitizado registrou um `SessionStart` de `startup` e dois `UserPromptSubmit` da mesma sessão. A diferença no diagnóstico se deve ao filtro de sessões novas do capturador. O payload de hook não identifica o host por si só: a atribuição ao VS Code vem da interação controlada pelo PI, do processo local da extensão `2.1.322` e da correlação temporal, com esse limite declarado.

O hook `Stop` foi acrescentado posteriormente, com SHA-256 da configuração local `5A375717B8AB6933A36E0048100331CB1699ACBEA8FFBAAC72C2DCE9A274750F`. Depois de outra interação no mesmo chat, o spool totalizou **cinco eventos** da mesma sessão: um `SessionStart`, três `UserPromptSubmit` e um `Stop`. O serviço mudou a presença de `trabalhando` para `aguardando` quando aplicou `Stop`.

O serviço local foi configurado para um projeto, uma fonte e captura de conteúdo desligada. Antes da interação, a API indicava fonte indisponível e zero sessões. Depois, mostrou fonte `atual`, um projeto, uma sessão e um agente de Claude em `arenahub`; o `Stop` projetou `aguardando`. O serviço foi reiniciado com o mesmo banco e spool: revisão e sequência permaneceram em `9`, com uma sessão e sem duplicação do feed; eventos posteriores continuaram a ser aplicados. No momento da checagem após `Stop`, a revisão era `11`. O spool tinha apenas `capturedAt`, `cwdHash`, `hook_event_name`, `prompt_id` opcional, `session_id` e `source`; nenhum campo de prompt, transcrição, comando, argumentos, resposta ou credencial. O snapshot HTTP não continha caminho absoluto do projeto, token do serviço nem chave de conteúdo de conversa. Os registros brutos dos chats não foram acessados.

## Conclusão e revogação

As duas primeiras tentativas não estabeleceram se a extensão emite hooks, porque o comando instalado falhava no Git Bash. A prova corrigida estabeleceu uma sessão real com início, submissões e espera na API, associada ao Claude Code do VS Code pela ação controlada do PI. **Player, dois projetos independentes, evento de ferramenta, subagente, tarefa, término nativo e perda/reconexão de fonte não foram comprovados.** Não há aceite funcional da #49.

Após a segunda tentativa, `.claude/settings.local.json` foi restaurado ao original e os arquivos temporários dessa tentativa foram removidos. A configuração da prova corrigida foi também **revogada** após o `Stop`: o arquivo foi restaurado byte a byte ao SHA-256 original `2775CB1496D074C037F5572DBF4C90291602C7A621927AEE2933C20017A0FAD2`; `.claude/settings.json` manteve seu hash original `F9C19FBF4F2D0A951C0F8100D52F8ED905E1F68F8D3198633D77FC538ECB6D31`. O serviço foi parado e os arquivos temporários desta prova (spool, banco, configuração, diagnóstico e backup) foram removidos. O checkout `arenahub` terminou com apenas o arquivo não rastreado preexistente `.impeccable/config.local.json`; a alteração alheia em `membership.test.ts` observada durante o ensaio já não constava no status final. Nenhuma delas foi alterada por esta integração.
